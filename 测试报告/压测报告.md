# 本地压力测试报告（v1.4）

测试对象：v1.4（`sms.cpp` 当前源码，`build.bat` 编译出的 `sms.exe`，464,384 字节）
测试日期：2026-10-02
测试性质：本地回环（loopback）压测，服务端与压测客户端跑在同一台 Windows 11 x64 机器上。

## 一、测试环境与方法

| 项目 | 配置 |
| --- | --- |
| CPU | 13th Gen Intel Core i9-13900HX（24 核 32 线程） |
| 内存 | 16 GB |
| 操作系统 | Windows 11 64-bit（Build 26200） |
| 编译 | VS 2026 Community `cl /nologo /EHsc /std:c++17 /W4 /utf-8`（`/W4` 零警告） |
| 压测客户端 | Node.js v24.20.0（`测试报告/harness.js`，每请求新建 TCP 连接 + `Connection: close`） |
| 被测对象 | v1.4 `sms.exe --server`，每轮独立临时目录 + 独立端口，种子数据预先写入 |

负载配方（8 客户端并发，与历史报告一致）：

| 占比 | 操作 |
| --- | --- |
| 40% | `GET /api/students?sort=total_desc` 查列表 |
| 20% | `GET /api/students?q=姓名关键字` 搜索 |
| 20% | `POST /api/students` 新增 |
| 10% | `PUT /api/students/<学号>` 改分 |
| 10% | `DELETE /api/students/<学号>` 删除 |

状态码 404（删除刚建/不存在的学号）是配方预期结果，**不算错误**；
只有网络层失败（连接被拒/重置、超时、进程崩溃）才计错误。

每轮临时目录里都放一份全新的 `sms.exe` + `students.txt` 种子数据，
数据文件按 EXE 目录定位（v1.3fix 行为），仓库里的 `students.txt` 全程未被触碰。

| 种子条数 / worker 数 | 请求总数 | 吞吐 | p50 / p95 / p99 | 最大延迟 | 错误 | 状态分布 200/201/404 |
| --- | --- | --- | --- | --- | --- | --- |
| 500 / 1 | 6,314 | **420.2 req/s** | 17.0 / 27.0 / 34.0 ms | 522 ms | **0** | 4558 / 1244 / 512 |
| 2363 / 2 | 4,156 | **276.7 req/s** | 26.0 / 38.0 / 181.0 ms | 424 ms | **0** | 2937 / 855 / 364 |
| 4599 / 1 | 1,791 | **118.9 req/s** | 63.0 / 97.0 / 242.0 ms | 390 ms | **0** | 1313 / 320 / 158 |
| 4599 / 2 | 2,501 | **166.2 req/s** | 43.0 / 64.0 / 277.0 ms | 536 ms | **0** | 1780 / 508 / 213 |

每轮结束均核对：接口条数 = 文件行数、无残留 `.tmp`（全部通过）。

## 三、边界场景

| 场景 | 结果 | 历史报告对照 |
| --- | --- | --- |
| 120 连接瞬时突发 | **65 成功 / 55 被重置**，整批 ~150 ms 结束，之后服务立即恢复 | v1.3.L 官方 65/55、v1.3fix 本机 65/55，三次一致 |
| 5 个"连上不发数据"的空闲连接 | 之后正常请求 **49.7 s** 返回 200（= 5 × 10 s 排队上限，不卡死） | v1.3fix 本机 50.0 s |
| 3 个半截请求（声称 500 字节 body 不发，顺序发） | 各 **10.0 s** 后返回 400，worker 随即释放 | v1.3fix 本机 10/20/30 s（当时为并行发） |
| 1.5 MB 超大请求头 | 服务端直接断开，不报错、不死锁 | 一致 |
| body 非 JSON / 方法不支持 / 路径不存在 | 400 / 405 / 404 | 一致 |
| `Transfer-Encoding: chunked` body | 400（服务端只认 `Content-Length`；浏览器与 curl 不发 chunked，无实际影响） | 与 v1.3fix 记录一致 |
| 进程资源（启动时） | 1 worker：**5 线程 / 5.42 MB**；2 workers：**6 线程 / 5.42 MB** | 与历史报告一致（5/6 线程、约 5.5 MB） |

持续写负载中 `taskkill -9` 强杀与重启核对属原子落盘范畴，见
[`原子测试报告.md`](原子测试报告.md)，结论：5 轮强杀后文件均 ≥3000 行完整，
重启后接口条数 = 文件行数、可继续写入。

## 四、写放大：吞吐为什么随数据量掉下来

四档数字呈现清晰的数据量相关性，根因有三层，都在设计与实现的可预期范围之内：

1. **整文件重写**：每增/删/改一次，`saveLocked()` 把全部记录重新写一遍
   （4599 条约 90 KB/次），复杂度 O(n)，与 Rust 版同源设计；
2. **真落盘才返回**：`MoveFileEx(..., MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`
   保证替换真正写入磁盘后才返回，写请求的墙钟时间被磁盘按住；
3. **全程持锁**：写与读抢同一把 `g_mtx`（GET 也要持锁拷贝整个 vector），
   所以 2 个 worker 在 4599 条时也只把吞吐从 118.9 拉到 166.2（1.4 倍）——
   贵在锁内的串行段，加线程摊不动它。

对本项目"本机单人使用"的定位：即便 4599 条、单 worker，119 req/s 也远超
单人操作频率；但几千条数据时写请求 p99 242 ms 在页面上是可感知的"转一下"。

## 五、与历史报告数字的对比

| 指标（500 条 / 1 worker / 8 客户端 × 15 s） | v1.3.L 官方 | v1.3fix 本机复现 | 本次 v1.4 |
| --- | --- | --- | --- |
| 吞吐 | 939.7 req/s | 602.7 req/s | 420.2 req/s |
| 延迟 p50/p95/p99 | 8.6/10.8/12.4 ms | 12.0/19.2/25.1 ms | 17.0/27.0/34.0 ms |
| 错误 | 0 | 0 | 0 |
| 120 突发 | 65/55 | 65/55 | 65/55 |

绝对值逐代下降主要来自客户端实现与同机 CPU 争用差异（历史客户端为一次性脚本、
实现未知；本客户端每请求新建连接并完整解析约 25 KB 的列表响应）。
**跨实现的相对结论完全一致**：零错误、背压计数 65/55、空闲连接 ~50 s、
半截请求 10 s 后 400、资源占用 5/6 线程。数字只在本报告内部横向可比。

## 六、结论

1. 正确性无问题：26 项接口断言全过，四档压测零错误，每轮接口与文件一致。
2. 背压与超时行为（约 65/120、空闲 10 s/连接）是 v1.2 起明确的设计取舍，
   历次复现稳定，不是缺陷；要支持多人高并发需要动的是这三处参数。
3. 写放大随数据量增长明显，目录级文档已在 README「实现要点」说明；
   数据量继续上涨时值得考虑增量落盘或写锁粒度拆分。
4. 新发现并记录在案的小瑕疵：`HEAD /` 附带完整响应体（RFC 要求 HEAD 无体），
   浏览器不触发，未修改代码，留待后续版本处理。
